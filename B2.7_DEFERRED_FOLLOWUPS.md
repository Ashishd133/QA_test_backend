## Resolved (was: blocked on Railway)

- [x] **Migration 016 (contract) got applied to `DATABASE_URL` earlier than
      planned** — a mistake, not a deliberate call: `uv run alembic upgrade
      head` was run against `DATABASE_URL` intending only to apply 017, but
      `head` always means the latest revision, so it applied 016 (the
      `scenarios.persona`/`persona_initials` drop) first without the
      planned check for a confirmed Railway deploy. Confirmed with the user

      **Forward-looking constraint, not a to-do**: `DATABASE_URL` no longer
      has the `persona`/`persona_initials` columns, so whenever Railway is
      next deployed, it must run code at or after B2.7-11 (commit
      `9567bc0`) — any older build will break immediately against this
      schema. Worth a reminder to whoever un-pauses the Railway services.

## From B2.7-11 verification (2026-09-28/29)

- [ ] **`test_dashboard_metrics_reconcile_with_seeded_fixture` now reliably fails** because
      `TEST_DATABASE_URL` carries real seed data (`uv run python -m app.seed`, run
      during B2.7-11 to verify the persona_id migration/seed changes) whose 4
      completed runs land inside the test's 7-day window (`testRuns7d` comes back
      `8` instead of `4`). This is the same structural issue already tracked above
      (global/unscoped dashboard count) — now actually triggered, not just
      theoretical, because the seed data is meant to persist. Not fixed; needs
      either project-scoping the endpoint or a different assertion strategy.
- [x] **`test_run_call_aggregate.py::test_parent_aggregate_matches_independent_reduce_over_children`
      is highly exposed to real Neon connection flakiness** — its own docstring
      documents ~40 fresh connection establishments per run (`null_pool=True`,
      no reuse) at ~12s each. Failed 4 consecutive times in this session with
      pure connection-layer errors (`TimeoutError`, `ConnectionResetError`,
      `ConnectionDoesNotExistError`, `BrokenPipeError` — never an assertion or
      logic failure), then passed cleanly on a 5th attempt once the network
      settled, confirming environmental flakiness rather than a B2.7-11
      regression. No action needed; noted in case the pattern recurs.

## Pre-existing, unrelated to any single ticket

- [ ] **CI's `judge-evals` workflow secret is broken** — `GCP_SERVICE_
      ACCOUNT_KEY_B64` is unset, so every run has failed since 2026-08-10
      with a `JSONDecodeError` before any real eval executes. Needs the
      secret populated in repo settings. See memory `ci_judge_evals_secret_broken.md`.
- [ ] **`test_dashboard_metrics_reconcile_with_seeded_fixture`'s
      `scenarioCoverage` assertion is structurally flaky** — `GET /v1/metrics/
      dashboard` computes scenario coverage from a global, unscoped `SELECT
      count(*) FROM scenarios`, so the test can only pass in a DB with zero
      other scenario rows. Needs either project-scoping the dashboard
      endpoint or a different assertion strategy. See memory
      `test_cleanup_outside_try_finally.md`.
- [ ] **Several DB test files call `_cleanup()` after, not wrapping, the
      `async with client` block** — a failed assertion inside that block
      skips cleanup and leaves orphaned rows that can pollute later runs
      (dashboard counts, unique-constraint collisions). Seen in
      `test_metrics.py`, `test_metric_backtest.py`, `test_claim_concurrency.py`,
      materialization tests. Worth a pass to wrap cleanup in `try/finally`
      around the whole test body. See memory `test_cleanup_outside_try_finally.md`.
